# Getting started

## Requirements

The repository targets Python 3.12. Model-backed experiments require local or downloadable access to the analyzed model weights. Feature proposal or classification stages may also require Ollama, Groq, or OpenAI, depending on configuration.

## Environment

From the repository root:

```bash
./setup.sh
```

Manual setup:

```bash
python3.12 -m venv .env
. .env/bin/activate
python -m pip install -U pip setuptools wheel
python -m pip install -r requirements.txt
python -m pip install -r code/studies/poisoning/requirements.txt
```

Run Python modules from `code/` or add `code/` to `PYTHONPATH`.

## Provider credentials

Create `.secrets.env` in the repository root when required by the selected providers:

```bash
cat > .secrets.env <<'EOF_SECRETS'
export GROQ_API_KEY=""
export OPENAI_API_KEY=""
export HF_TOKEN=""
EOF_SECRETS
chmod 600 .secrets.env
```

Set only the credentials required by the selected configuration. See [Credentials](credentials.md).

## Artifact roots

```text
data/       persistent model-backed experiment outputs
cache/      reusable computation caches
results/    generated analyses, audits, tables, and figures
code/       source packages and documentation
```

`data/` and `cache/` are not regenerated by the reporting driver. `results/` contains derived products.

## Inspect the overtopping study

From the repository root:

```bash
./run_overtopping_experiments.sh --list
./run_overtopping_experiments.sh --dry-run
```

The registry has no fixed required number of RunSpecs. `--list` prints the current settings and totals. It is organized into four execution sets:

```text
mean-donor     20
6-7b-models     4
mean            8
checkpoints    24
```

The checkpoint set is Grammar/HANS-NLI/Random-FSM × {step0, step48000, step96000, final `pythia-1b`} × {I+O, Out}; Arithmetic is not checkpointed. The exact coverage is documented in [Overtopping experiment design](../experiments/overtopping.md).

Run or inspect one set with, for example:

```bash
./run_overtopping_experiments.sh --suite checkpoints --dry-run
```

Suite membership does not alter persistent result/cache paths; existing artifacts continue to be reused.

Targeted inspection can use scientific filters directly:

```bash
./run_overtopping_experiments.sh \
  --task arithmetic \
  --model EleutherAI/pythia-1b \
  --evaluation-split test \
  --dry-run
```

## Validate persistent addressing

Before running a large experiment batch, the registry/path contract can be checked without reading or writing experiment data:

```bash
cd code
python -m studies.overtopping.experiments.storage_contract
cd ..
```

The optional check reports the current phase/replacement counts and registry fingerprint and fails only if distinct scientific settings collide in a persistent evaluation path. It does not enforce a setting count.

## Run overtopping experiments

```bash
./run_overtopping_experiments.sh
```

The runner supports:

```text
--phase pipeline    execute model-backed stages
--phase analysis    analyze existing persistent outputs
--phase all         execute both
```

The repository launcher defaults to the held-out `test` evaluation split.

The numbered model-backed pipeline is documented in [Pipeline](../methods/pipeline.md).

### RQ3 model-backed stages

After held-out singleton evaluation, RQ3 uses:

```text
Stage 7b   graded agonist intervention
Stage 7c   threshold-event diagnostics
```

The graded step requires:

```text
flip_stats_by_neuron.csv
scores.csv
frozen_candidate_ranking.csv
```

and writes:

```text
<stage7 stats dir>/graded_agonist_intervention/
```

Threshold-event diagnostics produce aggregate candidate/control files such as:

```text
aggregate_flip_stats.csv
aggregate_unit_tests.csv
aggregate_binned_curves.csv
aggregate_activation_flip_rows.csv
```

## Generate analyses and manuscript products

From the repository root:

```bash
./generate_results.sh
```

Direct invocation from `code/`:

```bash
python -m reporting.generate_final_results \
  --data-root ../data \
  --results-root ../results \
  --primary-profile configured
```

The reporting sequence:

1. materializes the current configured study table;
2. records metric-specific applicability and availability;
3. computes RQ1 statistics and final-snapshot sensitivity analyses;
4. computes RQ2 regime-specific composition analyses;
5. aggregates RQ3 threshold and graded-intervention analyses;
6. generates Pythia and poisoning trajectory outputs for RQ4;
7. validates required reporting products.

The standard reporting path writes only under `results/` and rejects a results root inside `data/` or the repository `cache/` tree. The repository wrapper also validates the overtopping storage/addressing contract before reporting.

### RQ3 source resolution

An explicit aggregate threshold source can be supplied with:

```bash
python -m reporting.generate_final_results \
  --data-root ../data \
  --results-root ../results \
  --primary-profile configured \
  --spiking-source /absolute/path/to/threshold_diagnostics
```

The repository wrapper forwards reporting options, so the same source can be supplied from the repository root:

```bash
./generate_results.sh --spiking-source /absolute/path/to/threshold_diagnostics
```

## Cache policy

Do not delete model-backed caches to regenerate figures or statistics. Cache invalidation is required only when the cache's own scientific key or metadata no longer matches the requested computation. Changing an aggregate reporting population does not alter an experiment path or cache key.

See [Operations](../operations/README.md) for targeted regeneration commands.
